Migration paths

Migrations: from Endevor, ChangeMan ZMF, ISPW, SCLM & co. to CI/CD

MainframeGuru editorial

There is no single right way. Broadly, two strategies can be distinguished, and they can be combined one after the other.

MainframeGuru editorial

A · Coexistence / bridge

The existing library manager remains the system of record for build, promotion and approval; developers work (partly) in Git. Lower transition risk, but two worlds that have to be kept in sync.

B · Git-native

Git becomes the sole source; build, test and deployment are rebuilt, and the old library manager is retired. A bigger overhaul, but a single unified toolchain.

C · Switching library managers

Moving to a different mainframe SCM with Git integration. Vendor-documented routes are listed in the ISPW and Panvalet/Librarian sections.

Endevor (Broadcom)

Path A: Endevor Bridge for Git

Bridge for Git maps Endevor inventory locations to Git repositories and branches and synchronizes changes in both directions. Version 3.0 (Oct. 2025) introduced multi-branching and a new front end; 3.2.1 (May 2026) improved branch merging. Version 2.x loses support on 30 June 2027. In addition, Team Build enables change-based builds; since 1.11.0 there has been a simplified export for Bridge for Git workflows. In parallel, Endevor 19 extends the API and CLI interfaces (e.g. approver groups via REST API v2).

Path B: Git + DBB

Elements are unloaded to PDS and transferred into repositories with the DBB Migration Tool or the DBB Git Migration Modeler. Endevor processors are translated into DBB language configurations (since DBB 3.0.2, a JCL-to-YAML tool helps). The publicly documented HCSC migration covered around 294,000 elements, 150+ applications and 15 DBB language processors; Endevor’s “Delete Behind” functionality was replicated.

Two projects delivered by IBM Expert Labs with the service provider Q Group are documented in detail, each in an IBM Expert Labs success story, available via the Q Group website: Atruvia (about 3.6 million elements, Bitbucket, Jenkins, DBB, UrbanCode Deploy) and dwpbank (about 181,000 elements, GitLab with z/OS runners, DBB, Wazi Deploy). According to the stories, both were planned to be delivered iteratively to avoid the risks associated with a turn-key approach, migrated in tranches of application bundles, moved only the latest three versions of each element to Git, and archived older versions automatically for audit purposes with the Q-Wing tool (see automated migration).

Sources: Broadcom (B4G 3.0), Broadcom (EoS 2.x), Royal Cyber (HCSC), Q Group (Atruvia), Q Group (dwpbank)

ChangeMan ZMF (Rocket Software)

ChangeMan ZMF has belonged to Rocket Software since May 2024 (acquisition of OpenText’s AMC business). Rocket promotes a native Git integration in which change packages are mapped to Git, plus REST APIs and a Zowe CLI plug-in. The Git-native path involves unloading the sources to Git and rebuilding build and deployment; a public user report from OneMain Financial (2021 talk) describes a move from ChangeMan to GitLab with DBB. According to a Legacy IT Center report (Oct 2025), UBS plans to switch from ChangeMan to Dependency Based Build for deployment; CROZ’s summary of a 2025 conversation with a UBS COBOL expert says UBS is “moving away from ChangeMan toward IBM Dependency Based Build (DBB)”, and CROZ’s key takeaways include “Bridge first, then evolve.”

Rocket has announced a virtual user group for December 2026 with sessions on a new VS Code extension, the product roadmap and a “new Git integration for ChangeMan ZMF” (demo on 15 Dec 2026).

Sources: Rocket, OpenText, IBM Z Customer Council, Legacy IT Center (UBS), CROZ/UBS, Rocket user group 2026

ISPW / BMC AMI DevX Code Pipeline

BMC positions Code Pipeline as a build and deploy engine that can be combined with Git (GitHub, Bitbucket and others): developers work with branches and pull requests, while Code Pipeline handles dependency-based generation, promotion and deployment. For moving from other SCMs to Code Pipeline, BMC cites its own methodology with a “Migration Discovery Tool”. According to the IBM Z DevOps Guide, source in other SCMs is unloaded to PDS libraries first and then migrated to Git.

For supply-chain evidence, BMC documents that Code Pipeline generates a CycloneDX software bill of materials (SBOM) for the components it manages – program names and versions, copybooks and called programs – via a batch job that can run as a pipeline step. Broadcom Team Build offers SBOM generation for Endevor-based builds with sbomz.

Sources: BMC Blog, BMC product page, Broadcom (Team Build sbomz), IBM Z DevOps Guide

SCLM (IBM)

According to a LinkedIn post by Marna Walle (IBM), IBM had planned to remove SCLM in the release after z/OS 3.2 and changed this plan based on user feedback. In an update of 27 Oct 2026 in the IBM Community thread “Infrastructure Management Deprecations”, IBM states that it “intends to remove Software Configuration Library Manager (SCLM) from a future release of z/OS”; among the actions it lists: “Evaluate Git, available through IBM Open Enterprise Foundation for z/OS (5655-OEF), or IBM Developer for z/OS Enterprise Edition (5755-AB5) as potential replacements.” According to the IBM Z DevOps Guide, IBM provides the SCLM-to-Git Migration Tool, “a set of scripts that extract SCLM data and place it in the target Git repository”.

Sources: LinkedIn post by Marna Walle (IBM), IBM post “Update: Planned removal of Software Configuration Library Manager (SCLM)” (Infrastructure Management Deprecations, 27 Oct 2026), IBM Z DevOps Guide (SCLM-to-Git Migration Tool)

Panvalet and Librarian

Broadcom documents conversion utilities from Panvalet and Librarian to Endevor. For the direct route to Git there is a public example: M&T Bank replaced its roughly 30-year-old Panvalet with Git/GitLab plus DBB, SonarQube and Ansible.

Sources: Broadcom TechDocs, IBM Community (M&T Bank)

Automated migration: which approaches exist?

MainframeGuru editorial

With tens of thousands to hundreds of thousands of elements, manual migration is not an option. Four categories of automation are publicly described – this overview makes no claim to completeness:

1 · Vendor utilities for source transfer

IBM DBB Migration Tool (copies PDS members into a Git repo on zFS, sets code page tags and .gitattributes, reports problematic characters), DBB Git Migration Modeler (open source: detects application boundaries based on naming conventions, analyzes copybook usage, generates build properties, repositories and pipeline templates; version 2.0 targets the DBB zBuilder only and can add sources incrementally to existing repositories), SCLM-to-Git Migration Tool.

2 · Translating build logic

The JCL-to-YAML migration tool in DBB 3.0.2+ generates zBuilder language configurations from existing build JCL. According to IBM, a “scan only” option “creates the build metadata without actually building any programs”. For Endevor processors, type, processor group, system, subsystem and environment have to be mapped dynamically.

3 · Synchronization during the transition

Bridges such as Endevor Bridge for Git, the Code Pipeline Git integration or the ChangeMan Git integration allow a gradual transition. Lifecycle orchestrators also advertise synchronization between the legacy SCM and Git during the transition phase.

4 · Service provider tools & accelerators

Service providers add their own tools and process models on top of the vendor utilities – above all for reading the legacy SCM including history, delta synchronization, archiving and validation. Examples: Q-Wing (Q Group, Endevor → Git with history and archive), the four-phase model of Royal Cyber (Discover → Migrate → Validate → Enable), the history-preserving migration utilities of PopUp Mainframe (ChangeMan, Endevor, Code Pipeline). The descriptions are based on the providers’ own publications.

What matters in automated migration

MainframeGuru editorial

  • History: current state only, last n versions or full history? Where does non-migrated history go (archive for audit)?
  • Integrity: hex comparison, record formats (FB/VB), non-printable and non-round-trippable characters, record lengths.
  • Delta runs: if development continues in parallel, changes must be carried over until cutover.
  • Application boundaries & repo layout: monorepo vs. one repo per application, shared copybooks.
  • Build equivalence: comparing newly built load modules with production (e.g. through test runs or binary comparison).
  • Processes: approvals, emergency fixes and promotion paths cannot simply be migrated – they have to be redesigned.

According to IBM, since DBB 4.0 zBuilder can publish and import versioned build packages across repositories (cross-application dependencies).

Sources: IBM DBB Migration Tool, DBB Git Migration Modeler, DBB 3.0.2, DBB 4.0, Migration Recipes (PDF), Royal Cyber four-phase model, PopUp Mainframe, Q Group Q-Wing, CROZ mainframe services, Living Mainframe references

Typical pitfalls

Code pages and special characters

MainframeGuru editorial

Source code is stored in EBCDIC (e.g. IBM-1141 in German-speaking countries). Git servers typically work with UTF-8. Non-round-trippable characters (for example in hex literals) must be detected and treated as binary if necessary.

The IBM Z DevOps Guide describes how the DBB Migration Tool handles code pages and reports problematic characters.

The zopen community port of Git applies encoding conversion and file tagging in 3-way merges, cherry-picks, rebases and stashes, and offers an opt-in transliteration fallback (core.iconvtranslit) for characters without an EBCDIC equivalent. With the strict default, conversion stops with an error when a character has no EBCDIC equivalent, so no character is substituted. News

Initializing dependency metadata

MainframeGuru editorial

For incremental builds to work, the build system needs the dependencies – either from a full build (costly, produces new modules) or from a scan without compiling.

According to IBM, DBB 3.0.2 and later offer a “scan only” option that “creates the build metadata without actually building any programs” (IBM Community).

Processors and special cases

MainframeGuru editorial

Decades-old processors contain options, pre-compilers, link-edit rules and exceptions. Inventorying them completely is often the single biggest effort.

Approval and emergency processes

MainframeGuru editorial

Package approvals, emergency fixes and delete-behind logic must be recreated in pull request rules, pipeline gates and deployment automation.

Approvals that live outside the pipeline (for example by email) can become a bottleneck when changes arrive faster.

In a Techstrong PulseMeter poll of 145 mainframe delivery practitioners and decision-makers (report sponsored by BMC, November 2026), 25% use AI for deployment automation and 26% for security and compliance automation. A DevOps.com article on the poll, labeled “Sponsored Content” and based on a webinar with BMC, recommends making policy checks, approvals and audit evidence outputs of the pipeline itself. Survey report · Article

People

MainframeGuru editorial

Moving hundreds of developers to Git at the same time requires training, pilot teams, champions and simple entry-level tools.

According to an interview on the IBM Community blog, M&T Bank built “a straightforward web interface using Python” for its business analysts (M&T Bank).

A typical approach

MainframeGuru editorial

  1. Assessment: inventory, types, processors, promotion paths, interfaces, volume.
  2. Target picture: coexistence or Git-native? Repository layout, branching model, build/deploy tools.
  3. Pilot: a manageable but representative application, including Db2/CICS.
  4. Migration factory: automated transfer, validation, delta runs, wave planning.
  5. Enablement: training, documentation, support, feedback loops.
  6. Decommissioning: archiving the history, ending the legacy system’s license.
