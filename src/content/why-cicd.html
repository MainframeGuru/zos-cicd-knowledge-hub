Motivation

Why CI/CD on z/OS?

The reasons for switching are rarely purely technical. Usually the skills situation, company-wide standardization, speed, quality and compliance all come together. Here are the main drivers – each with publicly documented examples.

Skills · One standard: Git · Speed · Quality & testing · Compliance · Cost · AI · Risks · FAQ

1. Skills and developer experience

The mainframe workforce is getting younger: in the BMC Mainframe Survey 2025, millennials make up 51% and Gen Z 15% of respondents (BMC). People trained on Git, VS Code and pull requests find it hard to work with ISPF-centric library manager processes. Uniform tools across all platforms make knowledge transferable and shorten onboarding time.

Real-world example: UBS has been training its own junior staff for years and relies on Git, GitLab, CI/CD and modern IDEs so that COBOL developers use the same processes as colleagues on other platforms (Legacy IT Center, in German).

2. One standard for the whole enterprise

Git is the de facto standard for version control. Keeping mainframe code in the same system enables shared reviews, security scans, permission and audit models, and cross-platform releases. IBM argues that Git should be the authoritative source for code, pipeline definitions and configuration – rather than being permanently synchronized with a legacy library manager (Planet Mainframe). Other vendors deliberately focus on coexistence (e.g. Endevor Bridge for Git, Code Pipeline with Git, ChangeMan Git integration) – see Migrations.

3. Speed and parallel development

  • ANZ Bank: hotfixes that used to mean around four weeks of effort for retrofit and deployment now take one hour at most, according to an IBM case study (IBM).
  • Nedbank: build-to-production reduced from hours to around 18 minutes, deployment cycles from 2–3 months to around 3 weeks (BMC).
  • Incremental builds: dependency-based builds compile only what changed and what is affected – a BMC internal team reports a reduction from around 90 to 3 minutes (BMC).

Branches instead of check-out/check-in allow several developers to work on the same program at the same time.

4. Quality through automated testing

Unit tests for COBOL and PL/I are now widely available and increasingly generated with AI assistance (e.g. IBM Test Accelerator for Z 3.0, BMC AMI DevX Unit Test (beta)). Integration tests against real z/OS systems can be automated with the open-source framework Galasa, static analysis e.g. with SonarQube (COBOL). In a pipeline, these become quality gates.

5. Compliance and traceability

Regulated industries need a complete trail from the business change to the module in production. Modern toolchains provide this through commit history, pull request approvals, build metadata (e.g. DBB build maps), SBOMs (e.g. Broadcom sbomz) and deployment evidence (e.g. Wazi Deploy, which from 3.0.8 can also store it in Db2). What matters is that this chain is designed deliberately – Git alone does not provide it (TechChannel).

6. Cost and tool landscape

Some case studies cite significant savings in license costs – ANZ, for example, around 90% compared with its previous mainframe SCM (IBM). Such figures come from vendor sources and depend heavily on the original contract. New costs arise for build/deploy tools, pipeline infrastructure, migration and training.

7. AI needs modern pipelines

In 2026, IBM (Bob Premium Package for Z, Pipeline Automation for Z), BMC (Code Pipeline MCP Server) and Rocket announced AI features for mainframe development. AI assistants work best with code in Git and automated build/test loops that check changes immediately.

Risks and counterarguments – an honest look

  • Culture: “The technical change was big, but the cultural change was decisive” – that is the gist of what ANZ says. Training teams and bringing them along is critical to success.
  • Loss of proven processes: library managers bundle promotion, approvals and emergency procedures. These must be deliberately recreated in the new world.
  • Character sets: EBCDIC content with non-printable or non-round-trippable characters needs a strategy (IBM Z DevOps Guide).
  • Security: code leaves the z/OS security domain; permissions, secrets and runner access must be designed carefully.
  • Big bang: many successful projects migrate step by step, application by application.
