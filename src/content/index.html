What does CI/CD on z/OS mean?

Continuous integration and continuous delivery (CI/CD) means that every change to the source code is automatically built, checked and delivered reproducibly all the way to the target environment. On the mainframe, this replaces traditional library manager processes that are often decades old – or complements them step by step. A typical chain looks like this:

  1. Git (source code)
  2. CI orchestration
  3. Dependency-based build
  4. Quality & security
  5. Unit/integration test
  6. Artifact repository
  7. Deployment & evidence

Important: Git alone is not a lifecycle. Build, tests, approvals, deployment and traceability have to be designed deliberately – trade articles in 2026 explicitly point this out (see TechChannel, Planet Mainframe).

The building blocks at a glance

Source control

Git (GitHub, GitLab, Bitbucket, Azure Repos) as the “single source of truth” – or synchronized with an existing library manager (e.g. Endevor Bridge for Git, ChangeMan Git integration, Code Pipeline with Git).

Build

IBM Dependency Based Build (DBB) with zBuilder (YAML) or zAppBuild (Groovy), Broadcom Team Build, BMC AMI DevX Code Pipeline – or existing JCL, triggered from the pipeline.

Orchestration

Jenkins, GitLab CI (including a native z/OS runner), GitHub Actions, Azure DevOps. Access to z/OS via SSH, z/OSMF REST APIs or Zowe CLI.

Test & quality

COBOL unit tests (e.g. IBM Test Accelerator for Z, BMC AMI DevX Total Test / Unit Test), integration tests with Galasa, static analysis e.g. with SonarQube (COBOL).

Deployment

IBM Wazi Deploy (Python/Ansible), Red Hat Ansible for z/OS, IBM DevOps Deploy (UCD), vendor features of the SCM suites – including deployment evidence for audits.

Developer experience

VS Code with Zowe Explorer, Code4z, BMC Workbench or IBM Z Open Editor; Eclipse-based IBM Developer for z/OS. Increasingly, AI assistants with z/OS context.
