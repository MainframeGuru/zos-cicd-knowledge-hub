Was bedeutet CI/CD auf z/OS?

Continuous Integration und Continuous Delivery (CI/CD) heißt: Jede Änderung am Quellcode wird automatisch gebaut, geprüft und reproduzierbar bis in die Zielumgebung ausgeliefert. Auf dem Mainframe ersetzt das klassische, oft jahrzehntealte Library-Manager-Prozesse – oder ergänzt sie schrittweise. Typischerweise entsteht eine Kette wie:

  1. Git (Quellcode)
  2. CI-Orchestrierung
  3. Abhängigkeitsbasierter Build
  4. Qualität & Security
  5. Unit-/Integrationstest
  6. Artefakt-Repository
  7. Deployment & Evidenz

Wichtig: Git allein ist noch kein Lifecycle. Build, Tests, Freigaben, Deployment und Rückverfolgbarkeit müssen bewusst gestaltet werden – darauf weisen Fachbeiträge 2026 ausdrücklich hin (siehe TechChannel, Planet Mainframe).

Die Bausteine im Überblick

Quellcodeverwaltung

Git (GitHub, GitLab, Bitbucket, Azure Repos) als „Single Source of Truth“ – oder synchronisiert mit einem bestehenden Library Manager (z. B. Endevor Bridge for Git, ChangeMan-Git-Integration, Code Pipeline mit Git).

Build

IBM Dependency Based Build (DBB) mit zBuilder (YAML) oder zAppBuild (Groovy), Broadcom Team Build, BMC AMI DevX Code Pipeline – oder weiterhin JCL, ausgelöst aus der Pipeline.

Orchestrierung

Jenkins, GitLab CI (inkl. nativem z/OS-Runner), GitHub Actions, Azure DevOps. Zugriff auf z/OS über SSH, z/OSMF-REST-APIs oder Zowe CLI.

Test & Qualität

COBOL-Unit-Tests (z. B. IBM Test Accelerator for Z, BMC AMI DevX Total Test / Unit Test), Integrationstests mit Galasa, statische Analyse z. B. mit SonarQube (COBOL).

Deployment

IBM Wazi Deploy (Python/Ansible), Red Hat Ansible für z/OS, IBM DevOps Deploy (UCD), Herstellerfunktionen der SCM-Suiten – inklusive Deployment-Evidenz für Audits.

Developer Experience

VS Code mit Zowe Explorer, Code4z, BMC Workbench oder IBM Z Open Editor; Eclipse-basiert IBM Developer for z/OS. Zunehmend KI-Assistenten mit z/OS-Kontext.
