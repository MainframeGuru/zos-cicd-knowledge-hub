Migrationspfade

Migrationen: von Endevor, ChangeMan ZMF, ISPW, SCLM & Co. zu CI/CD

Es gibt nicht „den“ Weg. Grundsätzlich lassen sich zwei Strategien unterscheiden – und viele Organisationen kombinieren sie zeitlich hintereinander.

A · Koexistenz / Brücke

Der bestehende Library Manager bleibt System of Record für Build, Promotion und Freigabe; Entwickler arbeiten (teilweise) in Git. Geringeres Umstellungsrisiko, aber zwei Welten, die synchron gehalten werden müssen.

B · Git-nativ

Git wird alleinige Quelle; Build (z. B. DBB, JCL aus der Pipeline), Test und Deployment werden neu aufgebaut, der alte Library Manager wird abgelöst. Größerer Umbau, dafür eine einheitliche Toolchain.

C · Wechsel des Library Managers

Umstieg auf ein anderes Mainframe-SCM mit Git-Integration (z. B. auf BMC AMI DevX Code Pipeline oder von Panvalet/Librarian auf Endevor). Hersteller bieten hierfür eigene Migrationsmethoden an.

Endevor (Broadcom)

Pfad A: Endevor Bridge for Git

Bridge for Git bildet Endevor-Inventarorte auf Git-Repositories und -Branches ab und synchronisiert Änderungen in beide Richtungen. Version 3.0 (Okt. 2025) brachte Multi-Branching und ein neues Frontend, 3.2.1 (Mai 2026) Verbesserungen beim Branch-Merging. Version 2.x verliert am 30. Juni 2027 den Support. Ergänzend erlaubt Team Build änderungsbasierte Builds; seit 1.11.0 gibt es dafür einen vereinfachten Export für Bridge-for-Git-Workflows. Endevor 19 erweitert parallel die API- und CLI-Schnittstellen (z. B. Approver-Gruppen über REST API v2).

Pfad B: Git + DBB

Elemente werden in PDS entladen und mit dem DBB Migration Tool bzw. dem DBB Git Migration Modeler in Repositories überführt. Endevor-Prozessoren werden in DBB-Sprachkonfigurationen übersetzt (seit DBB 3.0.2 hilft ein JCL→YAML-Tool). Die öffentlich dokumentierte HCSC-Migration umfasste ca. 294.000 Elemente, 150+ Anwendungen und 15 DBB-Sprachprozessoren; Endevor-Verhalten wie „Delete Behind“ wurde per Deployment-Automation nachgebaut.

Quellen: Broadcom (B4G 3.0), Broadcom (EoS 2.x), Royal Cyber (HCSC)

ChangeMan ZMF (Rocket Software)

ChangeMan ZMF gehört seit Mai 2024 zu Rocket Software (Übernahme des AMC-Geschäfts von OpenText). Rocket bewirbt eine native Git-Integration, bei der Change Packages auf Git abgebildet werden, plus REST APIs und ein Zowe-CLI-Plug-in. Der Git-native Weg führt über das Entladen der Quellen nach Git mit Neuaufbau von Build und Deployment; ein früher öffentlicher Anwenderbericht stammt von OneMain Financial (ChangeMan → GitLab + DBB). Die UBS plant laut einem Gespräch von 2025 den Wechsel von ChangeMan zu DBB und verfolgt dabei „erst überbrücken, dann weiterentwickeln“.

Quellen: Rocket, OpenText, IBM Z Customer Council, CROZ/UBS

ISPW / BMC AMI DevX Code Pipeline

BMC positioniert Code Pipeline als Build- und Deploy-Engine, die sich mit Git (GitHub, Bitbucket u. a.) kombinieren lässt: Entwickler arbeiten mit Branches und Pull Requests, Code Pipeline übernimmt abhängigkeitsbasiertes Generieren, Promotion und Deployment. Für den Wechsel von anderen SCMs zu Code Pipeline nennt BMC eine eigene Methodik mit einem „Migration Discovery Tool“. Wer ISPW vollständig ablösen möchte, entlädt die Komponenten in PDS und migriert wie bei anderen Systemen nach Git + DBB.

Quellen: BMC Blog, BMC Produktseite, IBM Z DevOps Guide

SCLM (IBM)

IBM hatte z/OS 3.2 als letztes Release mit SCLM angekündigt; im Oktober 2026 wurde die Absicht auf „Entfernung in einem zukünftigen Release“ geändert. Als Ziel empfiehlt IBM Git (über IBM Open Enterprise Foundation for z/OS) bzw. IBM Developer for z/OS Enterprise Edition; für die Quellmigration gibt es das SCLM-to-Git Migration Tool. Fachbeiträge betonen, dass bestehende JCL-Builds zunächst aus der Pipeline aufgerufen werden können und DBB optional ist.

Quellen: IBM Community, TechChannel

Panvalet und Librarian

Broadcom dokumentiert Konvertierungs-Utilities von Panvalet bzw. Librarian nach Endevor. Für den direkten Weg nach Git gibt es ein öffentliches Beispiel: M&T Bank hat ihr rund 30 Jahre altes Panvalet durch Git/GitLab mit DBB, SonarQube und Ansible abgelöst.

Quellen: Broadcom TechDocs, IBM Community (M&T Bank)

Automatisierte Migration: Welche Ansätze gibt es?

Bei zehntausenden bis hunderttausenden Elementen ist manuelle Migration keine Option. Öffentlich beschrieben sind vier Kategorien von Automatisierung – die Übersicht ist neutral und erhebt keinen Anspruch auf Vollständigkeit:

1 · Hersteller-Utilities für die Quellübernahme

IBM DBB Migration Tool (kopiert PDS-Member in ein Git-Repo auf zFS, setzt Codepage-Tags und .gitattributes, meldet problematische Zeichen), DBB Git Migration Modeler (Open Source: erkennt Anwendungsgrenzen anhand von Namenskonventionen, analysiert Copybook-Nutzung, erzeugt Build-Properties, Repositories und Pipeline-Templates), SCLM-to-Git Migration Tool.

2 · Build-Logik übersetzen

Das JCL→YAML-Migrationstool in DBB 3.0.2+ erzeugt zBuilder-Sprachkonfigurationen aus bestehender Build-JCL. „Scan only“ befüllt Abhängigkeits-Metadaten ohne Full Build. Bei Endevor-Prozessoren müssen Typ, Prozessorgruppe, System, Subsystem und Umgebung dynamisch abgebildet werden.

3 · Synchronisation statt Big Bang

Brücken wie Endevor Bridge for Git, die Code-Pipeline-Git-Integration oder die ChangeMan-Git-Integration erlauben eine schrittweise Umstellung. Lifecycle-Orchestrierer werben zudem mit Synchronisation zwischen Legacy-SCM und Git während der Übergangsphase.

4 · Dienstleister-Accelerators

Mehrere Dienstleister bieten eigene Werkzeuge und Vorgehensmodelle (Discover → Migrate → Validate → Enable), u. a. für Historienübernahme, Delta-Synchronisation und Validierung. Leistungsumfang und Reifegrad sind öffentlich meist nur als Marketing beschrieben – vor einer Auswahl Referenzen und ein PoC mit eigenen Daten anfordern.

Worauf es bei automatisierter Migration ankommt

  • Historie: Nur aktueller Stand, letzte n Versionen oder vollständige Historie? Wohin mit nicht migrierter Historie (Archiv für Revision)?
  • Integrität: Hex-Vergleich, Satzformate (FB/VB), nicht druckbare und nicht round-trip-fähige Zeichen, Record-Längen.
  • Delta-Läufe: Wenn parallel weiterentwickelt wird, müssen Änderungen bis zum Cutover nachgezogen werden.
  • Anwendungsgrenzen & Repo-Schnitt: Monorepo vs. Repo pro Anwendung, gemeinsam genutzte Copybooks.
  • Build-Äquivalenz: Vergleich der neu erzeugten Load-Module mit Produktion (z. B. über Testläufe oder Binärvergleich).
  • Prozesse: Freigaben, Notfall-Fixes und Promotion-Pfade lassen sich nicht „migrieren“, sondern müssen neu entworfen werden.

Quellen: IBM DBB Migration Tool, DBB Git Migration Modeler, DBB 3.0.2, Migration Recipes (PDF), Beispiel Vier-Phasen-Modell (Dienstleister)

Typische Stolpersteine

Codepages und Sonderzeichen

Quellcode liegt in EBCDIC vor (z. B. IBM-1141 im deutschsprachigen Raum). Git-Server arbeiten typischerweise mit UTF-8. Nicht round-trip-fähige Zeichen (etwa in Hex-Literalen) müssen erkannt und ggf. als binär behandelt werden. Der IBM Z DevOps Guide beschreibt Optionen.

Abhängigkeits-Metadaten initialisieren

Damit inkrementelle Builds funktionieren, braucht das Build-System die Abhängigkeiten. Entweder Full Build (aufwendig, erzeugt neue Module) oder „Scan only“ (DBB 3.0.2+), um Metadaten ohne Kompilierung zu erzeugen.

Prozessoren und Sonderfälle

Jahrzehntealte Prozessoren enthalten Optionen, Pre-Compiler, Link-Edit-Regeln und Ausnahmen. Diese vollständig zu inventarisieren ist oft der größte Einzelaufwand.

Freigabe- und Notfallprozesse

Package-Approvals, Emergency-Fixes und „Delete Behind“-Logik müssen in Pull-Request-Regeln, Pipeline-Gates und Deployment-Automation nachgebildet werden.

Menschen

Hunderte Entwickler gleichzeitig auf Git umzustellen erfordert Schulungen, Pilotteams, Champions und einfache Einstiegswerkzeuge – M&T Bank baute z. B. eine einfache Weboberfläche für Business-Analysten.

Ein neutrales Vorgehensmodell

  1. Bestandsaufnahme: Inventar, Typen, Prozessoren, Promotion-Pfade, Schnittstellen, Volumen.
  2. Zielbild: Koexistenz oder Git-nativ? Repository-Schnitt, Branching-Modell, Build-/Deploy-Werkzeuge.
  3. Pilot: Eine überschaubare, aber repräsentative Anwendung inkl. Db2/CICS.
  4. Migrationsfabrik: Automatisierte Übernahme, Validierung, Delta-Läufe, Wellenplanung.
  5. Enablement: Schulung, Dokumentation, Support, Feedback-Schleifen.
  6. Abschalten: Archivierung der Historie, Lizenzende des Altsystems.
